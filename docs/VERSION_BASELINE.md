# ai-video-app 最高有效需求基线

基线日期：2026-09-08
基线名称：`V7.1-core + V5-must-add + V6-RACI + V4.1/V4.2-topic-patches`

## 结论

本仓库不把文件名中的版本号当成一条可以直接排序的单一版本链。几份文档分别属于“全局产品”“功能摸排”“上线行动”“API 管理”“素材库”和“千问方案”等不同轨道，因此最高有效基线采用**分层合并**：

1. `短视频全功能系统7.1.docx` 是产品、权限、额度、任务、安全和验收的核心基线。
2. `AI视频聚合平台——完整功能摸排与优化方案 V5.0.docx` 中标为“必须新增/必须优化”的内容，只要不与 V7.1 明确规则冲突，就进入必做范围。
3. `AI视频聚合平台——上线前后角色行动清单 V6.0.docx` 负责 RACI、上线前后动作和交接证据，不改写产品功能语义。
4. `补充说明文档 V4.1——角色分工与后台API管理模块.docx` 是角色职责与 API/Vault 治理的专题补丁。
5. `AI视频聚合平台开发执行文档_V4.2_素材库补充说明.docx` 是素材模型、回收站和素材操作的专题补丁。
6. `千问系统完整设计文档V6.0.docx`、`AI视频聚合平台——V1.5 版本新增与优化开发文档.docx` 与 `AI视频聚合平台——文档补遗与功能完善建议.docx` 只用于查漏；不能覆盖上述规则，也不能单独证明某项能力已实现。
7. `AI视频聚合平台——完整开发执行文档 V4.0.docx` 作为 V4.1/V4.2 的历史上下文保留；同一主题已有补丁时，以补丁为准。

“进入有效基线”不等于“当前仓库已经完成”。实际完成度以 [REQUIREMENTS_TRACEABILITY.md](./REQUIREMENTS_TRACEABILITY.md) 和可运行验证为准。

## 合并算法

每次实现或验收需求时，按以下顺序处理：

1. 将文档描述归一为可验收的能力，而不是照搬页面名或表结构。
2. 先放入 V7.1 的核心能力和明确 Phase 1/Phase 2 边界。
3. 合并 V5.0 的非冲突 must-add；若尚未实现，仍保留为“有效基线缺口”，不能降级成可选项。
4. 在 API/密钥主题上应用 V4.1，在素材主题上应用 V4.2；专题补丁优先于较泛的旧描述。
5. 使用行动清单 V6.0 给需求附加负责人、批准人、协作人、知会人和上线证据。
6. 使用千问 V6、V1.5 与补遗检查遗漏；只允许增加不冲突且可验证的内容。
7. 给每项能力标记“已实现 / 本地演示 / 待接入 / 后续”，并记录真实数据边界。
8. 只有代码、测试、运行截图或真实服务回执可以把状态提升为“已实现”；文档描述、按钮、假数据和已保存的密钥都不能作为完成证据。

## 冲突裁决

| 冲突点 | 统一裁决 |
|---|---|
| 不同文档都有 V6、V5、V4 等编号 | 版本号只在各自文档轨道内有效；跨轨道按“核心基线 + 专题补丁 + 行动覆盖 + 查漏”合并。 |
| V5 must-add 与 V7.1 明确规则冲突 | V7.1 的安全、权限、计费和阶段边界优先；V5 仅合并不冲突部分。冲突内容进入决策记录，不静默实现。 |
| 文档写了“接入/连接/发布”，但仓库只有界面或配置记录 | 一律按“待接入”处理。目录启用、密钥入库、格式校验或演示成功都不等于上游可调用。 |
| V4 文档建议 Flutter、Go、PostgreSQL、Redis/Asynq 等栈，而仓库已使用 React、TypeScript、Vite 和 Node.js | 当前栈继续作为本仓库实现载体；数据库、队列和对象存储要求作为生产升级门槛，不触发无依据的整体重写。 |
| 业务角色与行动清单角色混用 | 运行时业务角色固定为会员 `user`、代理 `agent`、超级管理员 `super_admin`；RACI 角色只描述谁负责动作，不自动获得系统权限。 |
| 超级管理员是否与会员端共用入口 | 采用独立入口、独立会话边界和服务端 RBAC；会员端不得隐藏一个可直达的超级管理页。 |
| 手机号可选，但找回密码依赖短信 | 注册不强制伪造短信验证；真实短信适配器接入前，在线找回明确禁用并走人工受控流程。 |
| 用户自有 API 与平台付费额度的优先级 | 每个任务显式选择且只选择一种额度来源；自有 API 不应因付费额度不足被误拦截，两种配额分别校验和记账。 |
| 密钥可以在前端输入，但安全文档要求服务端保管 | 商用凭据只能写入服务端加密 Vault，永不回显原文；浏览器中的掩码/指纹流程仅是本地演示，不得存放或提交真实生产密钥。 |
| 保存密钥后是否算平台在线 | 不算。必须同时具备适配器、凭据、健康检查和真实调用回执，才能标记为可用；当前六家平台执行器均未接入。 |
| 客户端上报用量能否扣减余额 | 不能。余额变化只能由服务端幂等账本产生；客户端用量事件只作非财务记录。 |
| 任务何时扣额 | 生产目标为“预留 → 成功结算 / 失败、取消、终止释放”；当前共享控制面尚无任务账本闭环，本地模拟扣额不能视为生产实现。 |
| 充值码与在线支付混淆 | 充值码原子核销是已实现的控制面能力；在线下单、收款、退款、对账均为待接入，二者不得互相替代。 |
| 佣金审核通过与真实转账混淆 | 浏览器演示账本和人工审核状态不代表微信、支付宝或银行已经转账；真实出款与对账待接入。 |
| 素材“导入”与文件上传混淆 | 当前只记录文件名、类型和大小；对象存储、上传字节、预览转码、下载和容量计量均未接入。 |
| 回收站使用独立副本还是素材状态 | 采用单一素材记录的软删除状态和保留期，避免 `assets` 与 `recycle_bin` 双写漂移；生产端由服务端执行恢复和到期清理。 |
| 数字人素材覆盖还是保留历史 | 目标采用版本追加和当前版本指针，不覆盖原始授权资产；当前版本化能力尚未实现。 |
| “发布”指站内内容还是社交平台 | 教程/公告的站内发布已由控制面支持；抖音等外部平台的一键发布需要独立 OAuth、授权范围和回执，当前未接入。 |
| 本地模拟输出是否算 AI 成片 | 不算。`demo://` 记录、进度计时器和占位下载不能作为供应商生成或媒体交付证据。 |
| 文档未说清且实现会产生外部费用或公开内容 | 默认不执行外部副作用，状态保持“待接入”，待获得账号、费用、授权和验收标准后再启用。 |

## V5 非冲突 must-add 的处理

以下能力在有效基线中仍是必做项，即使当前实现状态为“后续”：

- 六阶段导演式创作流程及各阶段可编辑、可恢复的状态；
- 工作流编排/画布与明确的模型节点、素材节点和输出节点；
- 提示词优化、草稿/自动保存、历史版本与可回退；
- 灵感/模板入口和可追溯复用；
- 模型对比或 PK 机制，但只有真实适配器和同口径评测存在时才能输出结果；
- 对功能开关、失败恢复、空状态和跨端数据一致性的补强。

它们不得用静态卡片或伪造结果“完成”。实现时必须同步更新追溯表、测试和验收证据。

## 行动清单 V6 的 RACI 落地映射

RACI 中 `A` 表示最终负责和批准，`R` 表示执行，`C` 表示必须协作，`I` 表示知会。下表是仓库执行映射；它不创建新的系统权限。

| 动作 | A | R | C | I | 必须留下的证据 |
|---|---|---|---|---|---|
| 确认有效基线、费用边界和上线范围 | 产品/业务负责人 | 产品与工程负责人 | 运营、合规 | 用户与代理 | 版本基线、范围差异、批准记录 |
| 准备供应商账号、商用授权、预算与凭据 | 业务负责人 | 获授权的账号负责人 | 安全、工程 | 超级管理员 | 授权范围、费用上限、密钥轮换记录；密钥不得进入仓库 |
| 开发、测试与缺陷关闭 | 技术负责人 | 工程团队 | 产品、运营 | 业务负责人 | 测试报告、构建产物、缺陷清单 |
| 生产数据库、队列、对象存储、监控与备份 | 技术负责人 | 运维/工程 | 安全、产品 | 运营 | 迁移、恢复演练、告警、容量和回滚记录 |
| 套餐、卡码、教程、公告、风控和用户治理 | 平台运营负责人 | 超级管理员/运营 | 产品、客服、财务 | 业务负责人 | 控制面回执与审计事件 |
| 充值、佣金、提现和财务对账 | 财务/业务负责人 | 财务与获授权运营 | 工程、合规 | 用户/代理 | 订单、支付回执、账本、人工复核与对账差异 |
| 用户验收与上线批准 | 产品/业务负责人 | 产品、运营和验收用户 | 工程 | 全体相关角色 | 验收清单、未决风险、上线签字 |
| 发布、监控、故障处置与回滚 | 技术负责人 | 运维/工程 | 产品、运营、供应商 | 用户/代理 | 发布版本、健康检查、事件记录、回滚结果 |
| 上线后数据与权限复核 | 业务负责人 | 超级管理员、安全/运维 | 财务、产品 | 工程与运营 | 权限清单、账本核对、密钥轮换和审计导出 |

## 阶段边界

- **当前可验收范围**：会员端、独立超级管理端、共享控制面、服务端认证/RBAC、卡码与额度账本、供应商目录/Vault 元数据、站内内容、风险策略和审计链。
- **有效基线缺口**：V5 must-add 的导演工作流、工作流画布、草稿版本、提示词优化、灵感模板和可信模型对比，以及共享任务/素材/佣金控制面。
- **外部接入门槛**：真实 AI、短信、支付、对象存储、转码/队列、平台发布、推送和真实出款。
- **Phase 2**：以 V7.1 明确后置的黑白名单、素材标签分组、项目模板复用、维护计划/暂停任务和多管理员细粒度权限为主；详见追溯表。

## 基线变更规则

新增文档或需求时，不直接改写本文件结论。先提交一条变更记录，至少包含：来源、受影响能力、与 V7.1/V5/V4.1/V4.2 的关系、数据迁移、安全/费用影响、验收条件和回滚方式。只有冲突裁决完成后，才提升基线版本。
